# Security policy

## Reporting a vulnerability

Please report privately through this repository's
[GitHub security advisories](https://github.com/mike548141/tuhura/security/advisories/new)
— **not** a public issue, and not by email.

This is a personal project maintained in spare time. Expect an
acknowledgement within about a week, on a best-effort basis with no
guaranteed remediation timeline. There is no bounty.

## What this repo currently contains

Stating this plainly so reports can be aimed usefully: as of now tūhura
is **pre-implementation**. The repo holds strategy, architecture,
decision records and research, plus a seed `site/index.html`. The
surfaces described below are largely *designed, not yet built*. A report
against the design is welcome and is cheaper to act on than one against
code — the architecture is the thing currently worth attacking.

## What is in scope

tūhura is planned as a static, offline-first PWA with **no backend, no
accounts, no login, and exactly one class of third-party code** — a
vendored map renderer and tile reader committed into `site/vendor/`. No
CDN, no analytics, no trackers, no package manager at runtime. That
removes most of the usual attack surface. What is left is the
interesting part:

- **Safety-adjacent data rendered wrongly.** This is tūhura's most
  serious class of bug and the one most worth reporting. The app shows
  land access, conservation boundaries, hunting areas, tides and track
  grades. A rendering, caching or version fault that makes private land
  read as public, shows a stale boundary as current, or drops a layer
  silently rather than visibly can put someone in legal or physical
  jeopardy. Default-deny is the design rule: absence of data must never
  render as permission.
- **The vendored dependency** (`site/vendor/`) — a tampered, mis-pinned
  or unlicensed vendored artefact, or a gap in the pinning guard that
  lets one in.
- **The service worker** — cache poisoning, a stale or wrong-origin
  response being served, or a versioning fault that pins a device to old
  map or boundary data.
- **Offline tile storage** (PMTiles in OPFS) — a crafted or corrupted
  archive that escapes parsing, corrupts adjacent stored data, or
  exhausts the device.
- **Imported and stored user data** — waypoints, tracks, notes and
  photos live on the device. GPX/GeoJSON import is untrusted input; any
  path where imported data becomes markup or script, or where one
  origin, page or profile reads or overwrites another's, is in scope.
- **Cross-device sync and sharing**, once shipped — the payload is
  end-to-end encrypted against a store that must never be able to read
  it. Weaknesses in the encryption, in key handling, in sync-code
  entropy, or any path that lets the server recover plaintext are all in
  scope, as is any leak of location history through metadata.
- **Location privacy generally.** Track and waypoint data is a precise
  record of where someone has been. Any unintended egress of it — to a
  log, a URL, a third party, a shared link wider than intended — is a
  vulnerability, not a feature request.

## What is not in scope

- **The absence of a backend, accounts or authentication.** Deliberate.
- **Data accuracy from upstream sources.** A wrong boundary in LINZ or
  DOC data is a content issue — please open a normal issue so it can be
  hedged or sourced differently. A bug in how tūhura *renders* correct
  data is in scope and belongs above.
- **Anything requiring physical access to an unlocked device.** Personal
  data is deliberately device-local and unencrypted at rest; that is a
  documented trade-off, not a defect.
- **Missing rate limiting, CSRF tokens, or session handling.** There are
  no sessions and no server to defend.
- **Your own deployment** of this code, and **third-party dependencies**
  — report those upstream.
- Reports generated by a scanner with no demonstrated impact.

## Privacy

The app collects nothing and has no server to send it to. Waypoints,
tracks, notes, photos and settings stay in the browser's own storage on
the device. There are no accounts, no cookies, no analytics and no
third-party requests. Network access exists only to fetch map data and
forecasts, and everything the app does in the field works with the radio
off.
